# CLAUDE.md

Корневой файл инструктажа для Claude Code в этом проекте.

## Обязательно при старте каждой задачи

1. Прочитать `/working-protocol.md` — рабочий протокол
   сессии (остановки, str_replace, отчёты, pre-commit
   проверки).
2. Прочитать `/design-system.md` — конвенции дизайна
   (классы, токены, паттерны вёрстки).

Эти файлы — источник правды. Если в них что-то противоречит
запросу пользователя — остановиться и спросить, не
импровизировать.

## Ключевые жёсткие правила

### Никаких inline-стилей в HTML

Запрещено использовать атрибут `style="..."` на элементах.
Всегда либо существующий класс из `/style.css`, либо новый
класс в `/style.css`.

Единственное исключение: динамические стили, задаваемые
из JavaScript в runtime (например, position элемента,
вычисляемая ширина, данные из пользовательского ввода).
Статичные оформительские стили — всегда через классы.

См. `/design-system.md` раздел про CSS-конвенции.

### Генерируемые файлы правятся только через генератор

`courses/index.html` собирается скриптом
`scripts/render_courses_hub.py`. Править сам HTML запрещено:
следующая перегенерация сотрёт правку, а CI-job `seo-artifacts`
сравнивает закоммиченное с выводом генератора и валит сборку.
Менять нужно шаблон внутри скрипта.

Это уже случалось: скриптовый проход по мета-тегам добавил
`og:image:width/height` во все страницы, включая сгенерированную,
и уронил CI.

Единственный генератор HTML — `render_courses_hub.py`.
`generate_sitemap.py` собирает `sitemap.xml`, он тоже
под проверкой `seo-artifacts`.

### `google9b84a06f40ea405c.html` не удалять никогда

Файл подтверждения владения доменом в Google Search Console.
Лежит в корне, отдаётся по
`https://davydov.my/google9b84a06f40ea405c.html`.

Google перепроверяет подтверждение периодически, а не однократно
при добавлении сайта. Пропадёт файл — слетит подтверждение,
и вместе с ним доступ к данным поиска и возможность отправлять
карту сайта.

Ограничения:

- содержимое менять нельзя ни на байт, включая завершающий перевод
  строки: его в файле **нет**, размер ровно 53 байта.
  Проверка: `shasum -a 256` даёт
  `ddcd5ce0ab04a37986ed1edaaa1b7ce1ea764c806a52f85fdc1e21af264578c1`
- не переименовывать, не переносить в подпапку, не заворачивать
  в редирект: Google запрашивает точный путь
- не добавлять в `sitemap.xml` — это не страница сайта.
  Сейчас не попадает сам собой: карта собирается из
  `assets/search-index.json` и списка `EXTRA_PATHS`, а не обходом
  файлов
- скриптовым проходам по `*.html` этот файл не подсовывать.
  `promote_articles_navbar.py` обходит `ROOT.rglob("*.html")`
  и файл не трогает только потому, что внутри нет блока
  `nav-links`. Новым массовым правкам добавлять явное исключение

Для null подтверждение отдельное — там `yzotop.github.io/null/`
и, возможно, другой способ.

### `promote_articles_navbar.py` пишет на месте, `--dry-run` у него нет

Скрипт обходит `ROOT.rglob("*.html")` и **сразу перезаписывает**
подходящие файлы. Он не показывает, что собирается сделать, —
он это делает, а печатает уже список изменённого.

Запускать только осознанно, когда правка навигации и есть задача.
Не запускать «посмотреть, что он найдёт»: это уже случилось и молча
изменило три файла статей, которые пришлось откатывать через
`git checkout`.

Если посмотреть всё-таки нужно — сначала убедиться, что дерево
чистое, тогда результат виден в `git diff` отдельно от остального
и откатывается одной командой.

### Прежде чем звать ссылку битой — проверить, что curl вообще ходит

Вердикт «адрес недоступен» по одному `curl` может быть утверждением
о собственной машине, а не о сайте. Сначала контрольный запрос
на заведомо живой адрес:

```
curl -s -o /dev/null -w '%{http_code}\n' --max-time 15 https://davydov.my/
```

Не `200` — сеть сломана здесь, и любые выводы о чужих адресах
недействительны. Это уже случалось: `curl` отдавал `000` на
`yzotop.github.io`, и то же `000` на `davydov.my` — исходящий HTTPS
не работал вовсе (`SSL_ERROR_SYSCALL`). Браузерная панель в тех же
условиях отвечала `This site is blocked by policy`.

Обход, когда curl недоступен: `gh api` ходит другим путём и работает.
Существование страницы и состояние сборки проверяются так:

```
gh api repos/OWNER/REPO/pages --jq '.status, .html_url'
gh api repos/OWNER/REPO/pages/builds --jq '.[0] | .commit, .status'
```

### Зелёный CI не доказывает, что содержимое доехало

`site-qa.yml` проверяет репозиторий, а не отданные байты. Прогон может
быть зелёным, `pages build and deployment` — успешным, а живая страница
отдавать прежнюю версию.

После правки уже опубликованного содержимого проверять **содержимым**,
а не статусом:

```
curl -s "https://davydov.my/ПУТЬ/?v=$(date +%s)" | grep -c 'НОВОЕ ЧИСЛО'
```

Параметр `?v=` обязателен: без него легко прочитать собственный кэш
и отчитаться о том, чего не проверял.

Это уже случилось: правка сумм выручки в `ai-analyst-checks` была
объявлена опубликованной по зелёному CI, без проверки страницы.
Существующее правило «после пуша смотреть Actions, а не только curl»
работает и в обратную сторону.

### Одиночная ошибка lychee на `yzotop.github.io` — скорее всего шум

Локально `link-check` без кеша падает примерно в половине прогонов
с `Connection failed`, каждый раз на другом случайном адресе
`yzotop.github.io`.

**В CI это тоже случается**, хотя реже. Прежняя формулировка «в CI
этого нет» устарела: 28.08 прогон `3f01a81` упал на двух адресах
`yzotop.github.io` с `Connection reset by peer`, а перезапуск того же
задания без единой правки прошёл зелёным. Оба репозитория при этом
существовали и Pages были собраны — проверено через `gh api`.

Лечение в CI: перезапустить задание. Повторилось на **том же** адресе —
это настоящая поломка, а не шум.

Прежде чем чинить ссылку, проверить её `curl` — по упавшим адресам
стабильно 200. Сначала контрольный запрос, что curl вообще ходит
(см. раздел выше): иначе `000` на упавшем адресе означает поломку
сети здесь, а не там. Признаки шума, а не поломки: одна-две ошибки,
адрес каждый раз разный, все на одном хосте.

Признак настоящей поломки: ошибка повторяется на том же адресе
и воспроизводится curl.

Повторами это не лечится, проверено замерами — см. закрытый пункт
в `BACKLOG.md`.

### Зелёный link-check локально не доказывает зелёный в CI

Расходятся три вещи: версия lychee (у action своя; в workflow она теперь
закреплена как `v0.24.2` — до закрепления 0.22 и 0.24.2 на одном коммите
давали 2172 и 2853 проверки), IP запроса (домашний против датацентрового
у раннера — DDoS-Guard и подобные отбивают вторые) и потенциально вход.

Локальный прогон ловит битые ссылки, но не воспроизводит отказы
по репутации адреса. Если CI красный, а локально зелено — сперва
уравнять версию, и только потом искать разницу.

Отдельно: локальный прогон **вообще не проверяет внутренние ссылки**,
пока конфиг не переделан. `base_url` превращает `/cases/foo/`
в `https://davydov.my/cases/foo/`, а правило `^https://davydov\.my`
в `exclude` это отсеивает. Опечатка во внутреннем адресе проходит
и локально, и в CI молча — так уже случилось со ссылкой на ещё
не существовавший `/cases/ub22/palette/`.

Метод для любых расхождений между средами: уравнять всё, что можно
уравнять, и смотреть на остаток. Остаток и есть настоящая разница.

### `git stash` в рабочем каталоге не использовать

В дереве бывают чужие незакоммиченные правки — из параллельной сессии
или от автора. `git stash` забирает **всё** дерево, а не только своё,
и на время уносит чужую работу. Если между stash и pop что-то пойдёт
не так, восстанавливать её будет нечем.

Это уже случалось: `git stash push --include-untracked` ради проверки
«были ли эти ссылки битыми до правки» унёс вместе со своим и
незакоммиченный `design-system.md` из другой сессии.

Чем заменять:

- сравнить с прошлым состоянием: `git show HEAD:путь`,
  `git diff HEAD -- путь`, `git diff --quiet HEAD -- путь`
- проверить, менялся ли файл: `git diff --quiet HEAD -- файл` —
  если нет, он побайтово равен HEAD, и вывод о нём переносится
  на прошлое состояние без всякого stash
- нужна чистая копия — `git worktree add` во временный каталог,
  рабочее дерево при этом не трогается

### Карта сайта и поиск по сайту — разные вещи

`sitemap.xml` собирается из `assets/search-index.json`, но это **не**
означает, что содержимое обязано совпадать. Карта — заявка поисковику
«вот что индексировать»; поиск по сайту — навигация для того, кто уже
пришёл. Страницу можно убрать из карты, оставив находимой поиском.

Разводится списком `EXCLUDED_FROM_SITEMAP` в
`scripts/generate_sitemap.py`. Список защищён проверкой: если путь
в нём перестал существовать в индексе, скрипт падает с ненулевым кодом
и ничего не пишет — иначе опечатка молча вернула бы страницу в карту.

Правка `sitemap.xml` руками по-прежнему запрещена: CI-job
`seo-artifacts` пересобирает карту и делает `git diff --exit-code`.

### Замеры в браузере: сначала убедиться, что правило загружено

Перед любым измерением проверить, что своё правило действительно
присутствует в загруженной таблице стилей. **До** замеров, а не
после странного результата.

```js
[...document.styleSheets].reduce((n,s)=>{try{
  return n + [...s.cssRules].filter(r=>r.selectorText&&r.selectorText.includes('МОЙ-КЛАСС')).length
}catch(e){return n}},0)
```

Ноль — значит меряется старая страница из дискового кеша браузера,
и любые выводы о каскаде, специфичности и вёрстке будут ложными.
Лечится подменой `href` у `<link rel=stylesheet>` с новым query.

Это уже стоило трёх разборов на пустом месте: «правило специфичнее,
но не применяется», «компонент сломан на мобильном», «полоса
не помещается». Во всех трёх случаях правила просто не было
в загруженном документе.

### Ширина окна: `documentElement.clientWidth`, не `innerWidth`

Панель предпросмотра показывает страницу с отдалением (≈0.84),
поэтому `innerWidth` завышен: при раскладочной ширине 390 отдаёт 466.
Медиа-запросы и вёрстка считаются по настоящей ширине.

Для проверок «за экран не выходит» и «нет горизонтальной прокрутки»
сравнивать с `document.documentElement.clientWidth`. Сравнение
с `innerWidth` делает проверку мягче примерно на 20% — она
пропускает реальные вылеты.

### Координаты в SVG проставлены руками — кегль не трогать, только масштаб

Когда подписи внутри `<svg>` расставлены вручную фиксированными `x`/`y`,
менять кегль внутри нельзя — можно только менять масштаб самого SVG.
Первое ломает раскладку, второе сохраняет её точно.

Причина арифметическая, а не в невезении. Шаг между ярусами подписей
задан в единицах `viewBox` и не зависит от кегля. Если график ужимается
до 0.43× (760 единиц в 327 px), читаемые 10 физических px требуют ~26
единиц — больше, чем шаг между ярусами, и подписи налезают друг на друга.

Замерено на `/cases/telenok/`, шаг там 17 единиц:

```
кегль cap/num   столкновений   физический размер
11.5/13                0            4.9 px
12/13                  0            5.2 px   ← потолок без наложений
12.5/14                9            5.4 px
15/16                 18            6.5 px
```

Потолок вдвое ниже читаемости. Рабочее решение — обёртка с
`overflow-x: auto` и `min-width` на самом `<svg>`: при 700px подпись
выходит на 10.6 px, столкновений ноль, координаты автора не тронуты.

Обёртка должна охватывать **только `<svg>`**, а не весь `<figure>`:
иначе `<figcaption>` уезжает вбок вместе с графиком, хотя в 375 она
помещается целиком. Паттерн — `.table-wrap` из `/style.css`.

Проверять наложения замером, а не глазами: считать пересечения
`getBoundingClientRect()` у всех `<text>` внутри графика. Перекрытие
в 1–2 px визуально почти незаметно, но это уже сломанная раскладка.

### Pre-commit отчёт обязателен

Перед `git commit` всегда показывать пользователю:
- `git status` (точный список файлов)
- `git diff --stat` (масштаб)
- `git diff` по ключевым файлам (если объём <500 строк)
- Полный вывод `curl` по всем затронутым URL (HTTP-коды
  для каждого, не только сводку «всё 200»)
- Локальный прогон job `seo-artifacts` — он ловит расхождение
  генераторов до пуша:

  ```
  python3 scripts/generate_sitemap.py
  python3 scripts/render_courses_hub.py
  git diff --exit-code sitemap.xml courses/index.html
  ```
- Локальный прогон `link-check` — **обязательно без кеша**.
  `.lycheecache` не в репозитории, поэтому в CI его нет, а локально
  он держит устаревшие «OK» и даёт зелёный прогон при красном CI:

  ```
  rm -f .lycheecache && lychee --config lychee.toml './**/*.html'
  ```

После пуша — проверить статус Actions (`gh run watch --exit-status`),
а не только коды ответов по URL. Зелёный curl при красном CI
уже случался.

Без явного вывода всех проверок — не коммитить, ждать
явного «ок» от пользователя.
